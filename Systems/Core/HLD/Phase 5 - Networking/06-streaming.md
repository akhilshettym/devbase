## WebRTC & Video Streaming

### 1. High-Level Overview (The "Why" & "What"):

#### Real-World Analogy:

Digital media streaming operates across a spectrum defined by a fundamental trade-off: Latency vs. Scale & Efficiency.

```
+-----------------------------------------------------------------------------------+
| Real-World Analogy: Live Event Broadcasting                                       |
+-----------------------------------------------------------------------------------+
| WebRTC: Two-Way Walkie-Talkie / Direct Phone Call                                 |
| - Sub-second latency (< 500 ms). Ultra-fast, interactive bi-directional dialogue. |
| - High per-viewer server cost; connection state must be tracked individually for  |
| every active participant.                                                         |
|                                                                                   |
| HLS / DASH: Cable Television Broadcast with Buffer Delay                          |
| - Latency of 2–15 seconds. Data is chopped into static file chunks (.ts / .m4s)   |
| and served via standard web CDNs.                                                 |
| - Hyper-scalable to millions of passive viewers at minimal infrastructure cost.   |
+-----------------------------------------------------------------------------------+
```

- **WebRTC (Web Real-Time Communication)**: Solves the problem of real-time, peer-to-peer or server-mediated audio/video/data communication directly inside browsers without plugins. It achieves sub-second latency ($< 500\text{ ms}$) over lossy networks using UDP-based transport, dynamic bandwidth adaptation, and peer NAT traversal. Use WebRTC for Zoom-like video conferencing, online gaming, live auctions, interactive co-watching, and real-time remote control.

- **Buffered HTTP Streaming (HLS / Low-Latency DASH)**: Solves mass-scale media distribution. Instead of holding stateful media sockets open per user, the media is encoded into static segments and distributed over stateless CDN edge caches. Use HTTP streaming when broadcasting to thousands or millions of passive viewers where a 1–5 second delay is acceptable (e.g., Twitch, YouTube Live, Netflix).

### 2. The Basics (Scratch Level):

#### Core Terminology & Building Blocks:

- **Signaling**: The out-of-band process where peers exchange network metadata, security keys, and media capabilities to set up a connection (WebRTC does not define signaling; it can use WebSockets, REST, or HTTP-based protocols like WHIP/WHEP).
- **SDP (Session Description Protocol)**: A plain-text protocol format listing media capabilities (codecs,resolutions, frame rates, encryption keys, network parameters) generated by a client to establish a session.

#### NAT Traversal Stack:

- **NAT (Network Address Translation)**: Routers hide private local IPs (e.g., 192.168.1.5) behind public WAN IPs, blocking incoming unsolicited peer connections.
- **STUN (Session Traversal Utilities for NAT)**: A lightweight server queried by a client to discover its own public IP address and port mapping.
- **TURN (Traversal Using Relays around NAT)**: A relay server used when symmetric NATs or strict corporate firewalls block direct peer-to-peer traffic. Media is proxied through the TURN server over UDP/TCP.
- **ICE (Interactive Connectivity Establishment)**: The framework that gathers all candidate network paths (Local IP, STUN Public IP, TURN Relay IP) and tests them concurrently to pick the shortest,optimal working path.

#### Ingress & Egress Standards (WHIP & WHEP):

- **WHIP (WebRTC-HTTP Ingestion Protocol - RFC 9725)**: Standardized HTTP POST protocol to ingest WebRTC streams from encoders (e.g., OBS) into media servers without custom SDKs.
- **WHEP (WebRTC-HTTP Egress Protocol)**: Standardized HTTP POST protocol to pull WebRTC media streams out to playback clients.

#### Streaming Protocols Comparison Matrix:

| Protocol             | `Transport Protocol`       | `Target Latency` | `Scale Mechanism`                     | `Primary Use Case`                            |
| -------------------- | -------------------------- | ---------------- | ------------------------------------- | --------------------------------------------- |
| **WebRTC**           | SRTP over UDP              | 100–500 ms       | Stateful Media Servers (SFUs)         | Multi-party Video Calls, Interactive Live     |
| **RTMP**             | TCP                        | 1–3 seconds      | Custom Media Relay / Legacy Ingest    | Encoder Ingest (Legacy OBS to Twitch/YouTube) |
| **LL-HLS / LL-DASH** | HTTP/2 or H2/H3 (TCP/QUIC) | 1–3 seconds      | Traditional Stateless CDN Edge Caches | Low-latency Mass Live Streaming               |
| **HLS / DASH**       | HTTP/1.1 or HTTP/2         | 6–15 seconds     | Traditional Stateless CDN Edge Caches | On-Demand (VOD) & Standard Live Broadcasts    |

### 3. Deep Dive & Architecture (Mid Level):

#### WebRTC Connection Setup & Network Traversal Mechanics:

Establishing a WebRTC media channel requires a coordinated handshake across two distinct phases:Signaling (SDP Negotiation) and Connectivity Checks (ICE).

```
Peer A (Client) Signaling Server STUN Server Peer B (Client)
|                                   |                              | |
| 1. Query Public IP/Port ----------+----------------------------> | |
| <---------------------------------+-- Return Srflx Candidate ----| |
|                                   |                              | |
| 2. Create SDP Offer               |                              | |
| --- POST /offer (SDP + ICE) ----> | ----------------------------------------------------> |
|                                   |                              | | 3. Query Public IP/Port
|                                   |                              | <---------------------+
|                                   |                              | -- Return Candidate ->|
|                                   |                              | |
|                                   |                              <--------------------------- POST /answer (SDP) ----- | 4. Create SDP Answer
| <-- Deliver SDP Answer -----------|                               | |
|                                                                   | | |
|=== 5. ICE Hole-Punching Checks (Direct Peer-to-Peer Binding over UDP) ====================|
| <=======================================================================================> |
|                                                                                           |
| === 6. Encrypted Media Delivery (SRTP / DTLS Protocol) ===================================|
| <=======================================================================================> |
```

- **Offer/Answer Handshake**: Peer A creates an SDP Offer detailing its supported video codecs (e.g., VP8,H.264, AV1), audio codecs (Opus), and encryption keys. Peer B receives it, checks matching capabilities,and returns an SDP Answer.
- **ICE Candidate Gathering & Hole Punching**: Both peers query STUN servers to get Server Reflexive (srflx) candidates. They exchange these candidates via signaling. ICE performs UDP connectivity checks (STUN binding requests) to punch holes through both routers. If direct hole-punching fails (e.g.,Symmetric NAT behind strict enterprise firewalls), ICE falls back to a TURN Relay candidate (relay).
- **DTLS-SRTP Handshake**: Once a network path opens, peers perform a Datagram Transport Layer Security (DTLS) handshake over UDP to derive symmetric keys. All video/audio frames are subsequently encrypted using Secure Real-Time Transport Protocol (SRTP).

#### Media Server Topologies: Mesh vs. MCU vs. SFU

In multi-party video conferencing, raw peer-to-peer connections fail as room size grows due to exponential bandwidth scaling ($O(N^2)$).

1. Peer-to-Peer Mesh (O(N^2)) 2. MCU - Multipoint Control Unit (O(N)) 3. SFU - Selective Forwarding Unit (O(N))

```
   [ Client A ] <----> [ Client B ] [ Client A ] [ Client B ] [ Client A ] [ Client B ]
   ^ ^ \ / \ /
   \ / v v v v
   v v +-----------------+ +-----------------+
   [ Client C ] | MCU Server | | SFU Server |
   | (Decodes,Blends | | (Routes Packets |
   | & Re-encodes) | | Zero Transcode)|
   +-----------------+ +-----------------+
   | |
   v v
   [ Single Stream ] [ Multiple Streams ]
   | |
   v v
   [ Client C ] [ Client C ]
```

- **Mesh (P2P)**: Every client sends its media stream directly to every other client.
- **Bottleneck**: A room of $N$ participants requires each client to upload $N-1$ video streams. Collapses client outbound bandwidth for $N > 4$.
- **MCU (Multipoint Control Unit)**: Every client uploads 1 stream to a central server. The server decodes all incoming streams, resizes/blends them into a single "composite grid" video stream, re-encodes it, and sends 1 combined stream back to each participant.
- **Bottleneck**: Massive CPU overhead on the server due to real-time decoding and re-encoding.Introduces high server-side processing latency and limits video layout flexibility for the client.
- **SFU (Selective Forwarding Unit - Industry Standard)**: Every client uploads 1 stream to the SFU server.The SFU does not decode or re-encode the video. Instead, it operates as an intelligent L4/L7 media router, forwarding incoming packet streams directly to subscribers based on network conditions, dynamic view layouts, and speaker volume.
- **Advantage**: Minimal CPU consumption (zero transcoding), ultra-low processing latency ($< 10\text{ ms}$ routing overhead), and linear scaling ($O(N)$ outbound bandwidth).

### 4. Advanced Strategies & Trade-offs (Pro Level):

#### Production Optimization, Congestion Control & Scaling

1. Dynamic Bandwidth Adaptation: Simulcast vs. Scalable Video Coding (SVC)
   When an SFU routes Video Stream A to 50 viewers, some viewers are on high-speed fiber while others are on weak 3G mobile networks. Sending a single 4K stream will choke the mobile clients.

A. SIMULCAST (Client sends 3 independent streams)

```
Client Encoder ---> [ Low: 360p @ 300kbps ] ---> SFU ---> Mobile Viewer (360p)
---> [ Med: 720p @ 1.2Mbps ] ---> SFU
---> [ High: 1080p @ 4Mbps ] ---> SFU ---> Desktop Viewer (1080p)
```

B. SVC - Scalable Video Coding (Client sends 1 layered stream)

```
Client Encoder ---> [ Base Layer (360p) + Spatial Layer 1 + Spatial Layer 2 ] ---> SFU
|---> Mobile: Strips L1,L2 (Sends Base Only)
|---> Desktop: Forwards Full Stream
```

- **Simulcast**: The publishing encoder compresses and sends 3 distinct, parallel streams (Low, Medium,High resolution) to the SFU over a single WebRTC connection. The SFU dynamically inspects viewer bandwidth network feedback and forwards the appropriate stream tier to each client.
- **Trade-off**: Consumes ~30% more uplink bandwidth from the publisher, but is universally supported across hardware encoders and browsers.

- **SVC (Scalable Video Coding - e.g., VP9 / AV1)**: The encoder produces a single bitstream organized into hierarchical Dependency Layers (Base Layer + Temporal/Spatial Enhancement Layers). The SFU selectively drops enhancement layer packets for low-bandwidth clients without breaking the video decoder state.
- **Trade-off**: Highly bandwidth efficient on publisher upload, but requires modern CPU-intensive encoders and complex SFU layer dependency tracking.

#### 2. Network Congestion Control & Loss Recovery:

Because WebRTC runs over UDP, it must implement its own end-to-end transport congestion control and packet recovery:

- **Google Congestion Control (GCC) & TWCC**: The receiver tags incoming RTP packets with arrival timestamps and sends Transport-Wide Congestion Control (TWCC) feedback frames back to the sender. The sender detects queue delay build-up at intermediate routers before actual packet loss occurs,dynamically scaling down the encoder bitrate.

#### NACK (Negative Acknowledgments) vs. FEC (Forward Error Correction):

- **NACK**: Receiver detects a missing packet sequence number and explicitly requests a retransmission from the SFU over RTCP. Ideal when Round Trip Time (RTT) is low ($RTT < 100\text{ ms}$).
- **FEC (RED/ULPFEC)**: Sender embeds redundant error-correction parity packets alongside primary media packets. If Packet 3 is dropped, the receiver reconstructs Packet 3 using Packet 2 and the FEC parity packet without a network round-trip. Ideal on high-latency lossy links ($RTT > 150\text{ ms}$), at the expense of 15–30% extra bandwidth overhead.
- **Keyframe Requests (PLI / FIR)**: When a new viewer joins an SFU mid-stream or experiences heavy packet loss, it cannot decode P-frames until it receives a full I-Frame (Keyframe). The SFU sends a Picture Loss Indication (PLI) to the publisher to force the encoder to generate a immediate keyframe.

#### 3. Mass-Scale WebRTC Hybrid Architecture (WebRTC Ingest $\to$ HLS Egress):

Serving 500,000 passive viewers directly over stateful WebRTC SFU nodes is prohibitively expensive ($100\times$ cost vs. HTTP CDNs).

```
                                   HYBRID MASS-SCALE ARCHITECTURE

[ Publisher ] --(WHIP / WebRTC)--> [ Primary SFU Cluster ]
|
+------------------------+------------------------+
| (Sub-second Interactors) | (Real-time Broadcaster Stream)
v                          v
[ Interactive Viewers ] [ Transcoder & Segmenter ]
(WebRTC / WHEP, < 500ms) |
(Creates HLS Fragments)
v
[ Origin Shield / CDN ]
|
(Stateless HTTP Distribution)
v
[ Mass Passive Viewers ]
(HLS / LL-DASH, 1-3 sec)
```

- **Interactive Tier**: Key hosts, active speakers, and VIP interactors join a multi-region Cascading SFU Mesh using WebRTC/WHIP/WHEP for real-time sub-second communication.
- **Broadcast Tier**: The primary SFU forwards a copy of the RTP stream to a cluster of headless transcoders. The transcoders convert the stream into LL-HLS / HLS segments and push them to CDN Edge Nodes, scaling egress out to millions of passive viewers with 1–2 second latency at minimal cost.

### 6. Interview Checklist:

When pitching real-time media and video streaming systems in system design interviews:

- **Specify the Latency/Scale Target Early**: Clarify requirements immediately: "Are we building an interactive multi-party conferencing system requiring $< 500\text{ ms}$ sub-second latency (WebRTC/SFU), or a massive broadcast system for millions of passive viewers (HLS/DASH over CDNs)?"

- **Choose the Right Media Topology**: Always justify Selective Forwarding Units (SFUs) over Mesh or MCU topologies for multi-party video calls, citing zero-transcoding server efficiency ($O(N)$ bandwidth scaling, minimal CPU overhead).

- **Address NAT Traversal Explicitly**: Walk through the ICE framework, specifying how clients use STUNfor direct public IP discovery and fallback to TURN Relays over UDP/TCP port 443 when strict enterprise firewalls block direct peer connection setup.

- **Demonstrate Adaptive Bitrate (ABR) Depth**: Detail how to manage heterogeneous network clients on an SFU using Simulcast or SVC (Scalable Video Coding) paired with TWCC (Transport-Wide Congestion Control), NACK retransmissions, and FEC error correction.

- **Proactively Propose Modern Ingest Standards**: Pitch WHIP (RFC 9725) for standardizing WebRTC stream ingestion into media servers from broadcasters/encoders without requiring proprietary vendor client SDKs.
